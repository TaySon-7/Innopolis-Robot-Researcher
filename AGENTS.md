# Руководство для ИИ-разработчиков

## Область действия

Этот файл действует для всего репозитория. Если в подкаталоге появится свой
`AGENTS.md`, его более узкие правила дополняют или переопределяют этот файл для
соответствующей части проекта.

Приоритеты работы:

1. Сохранить корректность симуляции, навигации и подсчёта результатов.
2. Не смешивать скрытую истину сценария со знаниями агента.
3. Делать воспроизводимые изменения с проверками.
4. Не ломать Docker-сценарий запуска на macOS и Linux.

## Что это за проект

Robot Researcher — стенд ROS 2 Jazzy + Gazebo Harmonic для TurtleBot3 Burger.
Робот исследует шестиугольную арену с девятью столбами, ищет образцы,
учитывает стоимость грунта и должен вернуться на базу. В состав входят:

- `did_judge` — сценарии, физические ограничения, события, батарея и счёт;
- `did_agent` — карта стоимости, A*, навыки, автономная политика, HTTP API;
- `did_llm` — высокоуровневый LLM-планировщик;
- `dashboard` — основной React-интерфейс;
- `compose.yaml` — воспроизводимый запуск всего стенда.

Канонический способ разработки и проверки — Docker. На хосте не предполагается
установленный ROS 2.

## Критические инварианты

### Координаты и геометрия

- Карта отображается в мировой системе координат `odom`: арена и препятствия
  неподвижны, перемещаются робот, его след и маршрут.
- Лидар переводится в мировые координаты из позы сканера; нельзя рисовать лучи
  как локальные точки без поворота и переноса.
- Источник точной геометрии — живая сцена Gazebo через
  `/world/default/scene/info`, нормализованная в
  `did_agent/gazebo_geometry.py` и выдаваемая через `/api/geometry`.
- Константы React допустимы только как fallback при недоступной геометрии. Не
  создавайте второй независимый набор стен или столбов.
- В стандартной арене должна оставаться шестиугольная граница и ровно девять
  столбов. После изменений карты визуально сверяйте стены с возвратами лидара.

### Истина, знания и стоимость

- `/api/truth` и режим «Истина» существуют для оператора и отладки. Агент и
  LLM не должны использовать скрытые позиции образцов, будущих опасностей или
  неоткрытые изменения сценария.
- «Знания агента» строятся только из доступных роботу наблюдений.
- «Стоимость планировщика» разделяет `terrain`, `wall_cost`, их сумму и
  заблокированные клетки. При изменении схемы данных обновляйте backend-типы и
  React-типы одновременно.

### Управление и LLM

- LLM — только высокоуровневый планировщик. Он читает `/agent/state` и
  `/agent/status`, публикует `/agent/plan` и не должен напрямую писать в
  `/cmd_vel` или читать внутреннее состояние судьи.
- Допустимые подцели: `goto`, `search_around`, `collect`, `return_to_base`.
- Низкоуровневое движение, A*, реакция на лидар и перепланирование остаются в
  `did_agent`.
- План всегда проходит синтаксическую и предметную валидацию до исполнения.
  Ошибку следует вернуть планировщику для ремонта, а не молча исправлять
  произвольным образом.
- Ручная команда, новый план и смена сценария могут прервать текущий план. При
  остановке робот обязан получить нулевую скорость.

### Сценарии и seed

- `easy`, `medium`, `hard` — встроенные стабильные сценарии.
- `difficulty@seed`, например `hard@7`, — детерминированная генерация. Одинаковые
  сложность и seed должны давать одинаковые образцы, грунты, опасности и события.
- Предпросмотр в UI обязан показывать ту же раскладку, которая затем запускается.
- Динамические изменения `hard` применяются судьёй по времени симуляции, а UI
  должен различать текущее состояние и будущие события.

## Структура репозитория

```text
dashboard/                              React + TypeScript + Vite
  src/App.tsx                           компоновка и пользовательские действия
  src/ArenaCanvas.tsx                   карта, геометрия, лидар и слои стоимости
  src/ScenarioSetup.tsx                 выбор сложности, seed и предпросмотр
  src/AgentPanels.tsx                   журнал, LLM-план и управление агентом
  src/agentApi.ts                       HTTP-контракты и polling состояния
  src/rosbridge.ts                      WebSocket-подписки ROS
ros2_ws/src/did_judge/                  судья и YAML-сценарии
ros2_ws/src/did_agent/                  навигация, исполнитель и Agent API
  did_agent/dashboard_core.py           HTTP API и агрегированное состояние UI
  did_agent/dashboard_node.py           ROS-связи dashboard backend
  did_agent/gazebo_geometry.py          геометрия живой сцены
  did_agent/agent_node.py               исполнитель планов и автономный режим
  did_agent/costmap.py                  знания, грунт, стены и blocked-клетки
ros2_ws/src/did_llm/                    клиент, промпты, валидация и planning loop
ros2_ws/src/did_agent/web/index.html    старый standalone UI, не основной frontend
compose.yaml                            sim + dashboard
Makefile                                публичные команды разработчика
```

Новые функции интерфейса по умолчанию реализуйте в `dashboard/`. Не переносите
их автоматически в старый `did_agent/web/index.html`, если совместимость с ним
не входит в задачу.

## Базовый рабочий процесс

Перед изменениями:

1. Выполните `git status --short --branch` и сохраните несвязанные изменения
   пользователя.
2. Найдите затронутые контракты и существующие тесты через `rg`.
3. Определите источник истины для данных; не дублируйте геометрию, сценарии или
   ROS-состояние во frontend.
4. Вносите минимальное законченное изменение вместе с тестами.

После изменений:

1. Запустите минимальные релевантные тесты.
2. Затем выполните полную доступную проверку затронутого слоя.
3. Для визуальных изменений откройте React UI и проверьте реальную сцену, а не
   только успешную TypeScript-сборку.
4. Сообщите, что изменено, какие проверки выполнены и что не проверялось.

## Команды разработки

Все команды выполняются из корня репозитория.

```bash
make ui                 # собрать и поднять sim + React dashboard
make up                 # поднять уже собранные образы
make down               # остановить стенд
make check              # smoke-check ROS-стенда
make test               # полный Python-набор judge + agent + LLM в Docker
make test-fast          # тот же набор на подготовленном хосте
docker compose build    # проверить полную Docker-сборку
docker compose build dashboard  # TypeScript + production Vite build
docker compose ps       # проверить health контейнеров
make logs               # логи sim, judge, agent и LLM
```

Полезная диагностика:

```bash
make topics
make pose
make scan
make score
make events
make llm-state
make llm-status
```

LLM-режим запускается только осознанно:

```bash
make llm SCENARIO=hard@7
```

Он делает реальные внешние API-вызовы. Не запускайте его в тестах и не тратьте
API-бюджет без запроса пользователя. Без LLM обычные тесты должны быть полностью
детерминированными и сетенезависимыми.

## Правила по подсистемам

### Python и ROS 2

- Держите алгоритмы в обычных тестируемых Python-модулях, а ROS-ноды — тонкими
  адаптерами для топиков, сервисов, параметров и времени.
- Используйте `use_sim_time` для логики эпизода. Не смешивайте wall clock со
  временем Gazebo.
- Не блокируйте callbacks длительными сетевыми вызовами или ожиданием движения.
- Сохраняйте обратную совместимость ROS-топиков и JSON-полей либо обновляйте все
  производители, потребители и тесты одним изменением.
- Ошибки плана и API должны содержать понятную причину, пригодную для журнала и
  повторного планирования.
- Для логики движения добавляйте unit-тест на чистом ядре до длительной проверки
  в Gazebo.

### Agent HTTP API

- React обращается к `/api` через nginx; прямой backend доступен на `:8082`.
- Валидируйте числа, границы координат, сценарии и структуру планов на backend.
- Не доверяйте данным браузера и не допускайте записи произвольных файлов через
  API сценариев.
- При изменении ответа синхронно обновите типы в `dashboard/src/agentApi.ts` и
  тесты `did_agent/test/test_dashboard.py`.
- API не должен возвращать ключи, переменные окружения или содержимое LLM-запроса
  с секретами.

### React dashboard

- TypeScript должен собираться без ошибок через `pnpm build` в Dockerfile.
- Сетевые контракты описывайте в `agentApi.ts`, ROS-подписки — в `rosbridge.ts`;
  не размазывайте необработанный fetch/WebSocket-код по компонентам.
- Canvas должен учитывать `devicePixelRatio`, изменение размера и преобразование
  world-to-screen. Масштаб всех объектов вычисляется из одной геометрии.
- Ручное управление обязано останавливаться при `pointerup`, `pointercancel`,
  потере фокуса, скрытии вкладки и разрыве соединения.
- Не скрывайте ошибки агента: показывайте `failed`, `preempted` и причину в UI.
- Сохраняйте три режима карты отдельными: истина, знания агента, стоимость
  планировщика.

### Сценарии и судья

- Встроенные YAML находятся в `ros2_ws/src/did_judge/scenarios/`.
- Генератор и загрузчик должны проверять, что объекты находятся внутри арены,
  не пересекают запрещённую геометрию и сценарий остаётся проходимым.
- Изменение правил сбора, батареи, штрафов или событий требует теста модели
  судьи и проверки совместимости dashboard.
- `scenarios_custom/` — локальные генерируемые данные, не источник истины.

### LLM-планировщик

- Ключ задаётся только как `llm_api_key=...` в локальном `.env`; Compose передаёт
  его контейнеру как `DID_LLM_API_KEY`.
- Никогда не печатайте значение ключа. Разрешено сообщать только `set/missing`.
- Промпт не заменяет валидатор: любой ответ модели считается недоверенным вводом.
- Не импортируйте исполнитель в планировщик ради скрытого совместного состояния;
  связь подсистем идёт через опубликованные контракты.
- Сохраняйте безопасный fallback при недоступности модели и явно отображайте в
  UI, кто сейчас управляет: LLM-план или автономная политика.
- Тесты LLM должны использовать fake/stub-клиент, а не реальный endpoint.

### Docker и зависимости

- Большой слой ROS/Gazebo в `Dockerfile` держите стабильным. Новые небольшие
  Python-зависимости добавляйте через `requirements.txt`, не переставляя без
  причины тяжёлые apt-слои.
- Обновляйте lockfile при изменении frontend-зависимостей.
- Не добавляйте bind mount `.env` и не копируйте секреты в образ.
- После изменения launch/config/package metadata выполняйте полную сборку sim,
  потому что исходники копируются в образ и собираются `colcon`.

## Матрица проверок

| Тип изменения | Минимальная проверка |
| --- | --- |
| Документация | проверить команды и пути по текущему репозиторию |
| Чистая Python-логика | релевантный `pytest`, затем `make test` |
| ROS node/launch/package | `docker compose build sim`, `make up`, `make check` |
| React/TypeScript/CSS | `docker compose build dashboard` и визуальная проверка `:8080` |
| HTTP API | `test_dashboard.py`, production frontend build, smoke через UI |
| Геометрия/лидар/карта | unit-тесты, Gazebo runtime, визуальное совпадение стен и scan |
| Сценарии/seed | generator/judge tests, два одинаковых preview, фактический запуск |
| LLM planning | stub-тесты; реальный smoke только по явному запросу пользователя |
| Docker/Compose | `docker compose build`, `docker compose up --wait`, `docker compose ps` |

Если полная проверка невозможна, не выдавайте изменение за полностью
проверенное — явно укажите ограничение.

## Секреты и генерируемые файлы

Никогда не коммитьте и не добавляйте в Docker context:

- `.env` и API-ключи;
- `.venv/`;
- `logs/`, включая LLM exchanges;
- `ros2_ws/build/`, `ros2_ws/install/`, `ros2_ws/log/`;
- frontend build/cache artifacts;
- `scenarios_custom/`, если пользователь специально не просит зафиксировать
  конкретный сценарий.

Перед коммитом проверяйте `git status` и staged diff. Если секрет уже попал в
историю, одного удаления файла недостаточно — сообщите об этом пользователю и
не переписывайте опубликованную историю без явного разрешения.

## Git и границы изменений

- Рабочая интеграционная ветка проекта — `develop`.
- Не перезаписывайте и не откатывайте несвязанные изменения пользователя.
- Не выполняйте force-push, rebase опубликованной ветки или удаление данных без
  явного запроса.
- Не коммитьте и не отправляйте изменения автоматически: commit/push выполняется
  только когда пользователь это попросил.
- Коммит должен быть тематически цельным; в сообщении описывайте результат, а не
  процесс работы.

## Критерии готовности

Изменение считается завершённым, когда:

- реализован весь запрошенный пользовательский сценарий, а не только happy path;
- сохранены перечисленные выше инварианты;
- обновлены связанные backend/frontend-контракты и документация;
- добавлены или адаптированы релевантные тесты;
- выполнены проверки из матрицы;
- интерфейс проверен на реальном snapshot/потоке данных, если менялась
  визуализация;
- в diff нет секретов, виртуальных окружений, логов и случайных артефактов.
