# Математический планировщик: рабочая интеграция и автономный прототип

Рабочий запуск `make ui` использует `math_goals`: агент публикует варианты
в `/agent/state.goal_offer`, DeepSeek выбирает ID в отдельном потоке, а агент
повторно оценивает маршрут и батарею перед исполнением. LLM читает только
`/agent/state`, `/agent/status` и команды оператора. Свободные планы модели
без `goal_selection` рабочий агент отклоняет.

Выбор публикуется на `/agent/plan` с `goal_selection: {snapshot_id, goal_id}`,
источником `llm`, `fallback` или `budget` и готовыми подцелями из предложения.
Исполнитель использует собственные координаты цели. В состоянии дополнительно
публикуются `control_mode`, `decision_source`, `finished`; статусы сообщают
`plan_complete` и `subgoal_count`. Промежуточный `done` не завершает весь план.

Предложение остаётся стабильным во время API-запроса. Часы симуляции и небольшой
шум позы не отменяют выбор; карта, расход и батарея проверяются заново при приёме.
Смена эпизода, ручная команда или существенное перемещение отменяют старый выбор.
`goto` математического плана и локальный поиск контролируют запас на возврат
во время движения. При исчерпании запаса остаётся аварийная попытка возвращения:
она явно помечена и не означает гарантированный успех.

Команды `/agent/command`: `auto` — прежний автономный обход, `stop` — остановка,
`llm` — явное возобновление LLM. Новый эпизод начинает независимое планирование.

## Автономное демо

Запуск из корня проекта:

```bash
make planner-prototype
```

Нужен запущенный Docker. Команда собирает образ `did/robot-researcher:jazzy`
из текущих исходников, затем запускает отдельный контейнер с отключённой сетью,
без ключей и без ROS/Gazebo. Действующий стенд остаётся без изменений.

Прототип берёт карту проекта и **искусственное наблюдаемое состояние**. Он печатает
варианты целей, расчёт энергии, выбор заглушки и план в формате существующего
исполнителя. Статусы исполнения тоже искусственные: это проверка протокола,
а не эксперимент по качеству навигации или DeepSeek.

## Что реализовано

1. `did_agent.experimental_goals` создаёт цели из свободных клеток переданной
   карты знаний. A* считает маршруты; расход батареи учитывает грунт, а не
   искусственный штраф близости к стенам.
2. Цель допустима, если
   `E_туда + E_поиск + 1.4 × E_домой + 8 ≤ батарея`.
   Множитель расхода на метр задаётся отдельно. Длина поиска по умолчанию —
   оценка 3 м, не ограничение существующего навыка.
3. `did_llm.experimental_selector` передаёт модели варианты и целевую формулу
   `10N + 5R − 2C − F − 3H`. Коэффициенты берутся из констант правил судьи;
   состояние судьи, скрытые образцы и будущие события не передаются.
4. Модель возвращает только `{"goal_id":"…","reason":"…"}`. Бэкенд сверяет
   ответ с собственными целями и свежим состоянием, затем формирует
   `goto → search_around → collect` или `return_to_base`.
   Существующий исполнитель прекращает план при неудачном поиске, до `collect`.
5. Один разобранный JSON с неверным выбором возвращается модели для исправления.
   При повторной ошибке, неразбираемом ответе или недоступности модели
   используется явно обозначенный `fallback`: самый
   дешёвый допустимый поиск, иначе допустимый возврат. Когда нет допустимых целей,
   прототип возвращает ошибку и не выдаёт план движения.
6. Новый запрос запрещён до завершения **всего** плана. Изменившиеся батарея,
   эпизод, время или карта делают ответ устаревшим. Сброс сессии отменяет
   ожидавшиеся ответы; старые статусы не завершают новый план.
7. Цель попадает в историю только после результата исполнения. Завершённые и
   неудачные попытки не повторяются в том же эпизоде; прерванную попытку можно
   повторить. История попыток не означает обследование всего круга поиска.

## Где здесь математика и где ограничение прототипа

Формула счёта задаёт цель миссии. Для численного ожидания этого счёта пока нет
модели вероятностей обнаружения, столкновений и возврата, поэтому
`expected_score = null`. Прототип считает **энергетическую допустимость**;
заглушка и fallback минимизируют расход среди допустимых поисков, а не доказывают
оптимальность ожидаемого счёта.

Запас 1.4 и 8 — настраиваемая эвристика из существующего подхода, а не
доказательство 95% возврата. Поиск может уйти от центра и пройти больше 3 м;
расход и путь домой надо повторно проверять во время реального движения.
В рабочем исполнителе включён контроль бюджета во время движения. Калибровка
оценок по эпизодам всё ещё нужна для утверждений о вероятности успешного возврата.
Строгая проверка снимка с точным временем остаётся в автономном прототипе;
рабочий `GoalOffers` вместо неё повторно рассчитывает допустимость выбранной цели.

Это гибрид «LLM + вычислитель», без обучения сиамской сети. Сравнение с обычным
автономным алгоритмом на одинаковых seed и оценка DeepSeek — следующие эксперименты.

## Подключение настоящей модели к этому dry-run

Адаптер использует существующий `LLMClient`, принимает явно заданные endpoint,
имя модели и переменную `DID_LLM_API_KEY`. В подготовленном Python-окружении:

```bash
PYTHONPATH=ros2_ws/src/did_agent:ros2_ws/src/did_judge:ros2_ws/src/did_llm \
  python3 -m did_llm.experimental_demo --live \
  --base-url "<ваш endpoint>" --model "<идентификатор DeepSeek>"
```

Переменная ключа должна быть уже задана; по умолчанию `.env` не читается.
`--live` разрешает максимум два внешних обращения (ответ и одно исправление),
но по-прежнему только печатает план. `source` в выводе различает `stub`, `llm`
и `fallback`. Это отдельный запуск, не управление действующим роботом.

## Проверки

```bash
make test-planner-prototype
```

Тесты проверяют расчёт, границы бюджета, неизвестные и подменённые цели,
изменения карты без смены её версии, устаревшие ответы, ошибки модели и
жизненный цикл плана. Они используют заглушки и не требуют сети.
Рабочие модули: `did_agent.goal_offers`, `did_llm.math_planner` и их ROS-адаптеры.
Их дополнительные тесты включены в обычный `make test`; интерфейс показывает
контроллер, источник последнего плана и рассчитанный бюджет цели.
